# Оптимизации HH.uz — Защита от Rate Limit (429)

**Дата:** 2026-05-07
**Ветка:** `feature/hh-rate-limit-protection` → `main` (PR #2)

---

## Проблема

HH.uz API возвращал `429 Too Many Requests`, потому что:
- Для каждой вакансии уходили отдельные параллельные запросы
- Retry выполнялся немедленно (без backoff)
- Одинаковые запросы отправлялись повторно
- Загружалось слишком много страниц (40 штук)
- Каждый рекрутер работал независимо — без глобального контроля

---

## Реализованные решения

### 1. Light Check — лёгкая проверка (Проблема 1)

**Файл:** `backend/app/services/hh_service.py` — `find_search_variant()`

Перед полным запросом к HH делается проба с `per_page=1`.
Если результатов нет — переходим к следующему варианту, полный fetch НЕ выполняется.

```
Было:   вариант → загрузить 50 резюме → пусто → следующий вариант
Стало:  вариант → проба 1 резюме → пусто → следующий вариант (49 запросов сэкономлено)
```

---

### 2. Глобальный Rate Limiter + Центральная очередь (Проблемы 2 & 7)

**Файл:** `backend/app/services/hh_service.py`

```python
_HH_SEM: asyncio.Semaphore(3)   # макс. 3 параллельных HH-запроса
_guarded_get()                  # все GET-запросы к HH идут через него
```

- Все запросы к HH (rematch, live pool, ingestion) проходят через один `_HH_SEM`
- После каждого запроса внутри семафора — `asyncio.sleep(0.35s)`
- Это заменяет **центральную очередь**: сколько бы рекрутеров ни работало одновременно — к HH уходит не более 3 параллельных запросов

**Настройка (через `.env`):**
```env
HH_GLOBAL_CONCURRENCY=3    # по умолчанию: 3
HH_REQUEST_DELAY=0.35      # по умолчанию: 0.35 секунды
```

---

### 3. Redis-кэш результатов поиска (Проблема 3)

**Файл:** `backend/app/services/hh_service.py` — `_do_search()`

Результаты поиска `/resumes` кэшируются в Redis.

**Ключ кэша:** MD5-хэш от `text + area + experience + employment + page + per_page`

**TTL:** 1 час (3600 секунд)

```
1-й рекрутер: "Java Developer" → запрос к HH → сохранено в Redis
2-й рекрутер: "Java Developer" → получено из Redis (запрос к HH НЕ выполняется)
```

**Настройка:**
```env
HH_SEARCH_CACHE_TTL=3600   # по умолчанию: 1 час
```

---

### 4. Экспоненциальный Backoff (Проблема 5)

**Файл:** `backend/app/services/hh_service.py` — `_get_resume_detail_single()`

При получении 429 повтор не выполняется немедленно:

```
1-я попытка → 429 → ждём 2 сек → 2-я попытка → 429 → ждём 5 сек → СТОП (_RATE_LIMITED)
```

- Параллельный retry никогда не выполняется
- Через sentinel `_RATE_LIMITED` вызывающий код получает уведомление о пропуске

**Настройка:**
```env
HH_RETRY_BACKOFF=[2.0, 5.0]   # по умолчанию: [2.0, 5.0] секунды
```

---

### 5. Лимит страниц (Проблема 6)

**Файл:** `backend/app/routers/matching.py`

```python
# Было:
MAX_PAGES = 40  # 40 × 50 = 2000 резюме

# Стало:
MAX_PAGES = settings.hh_max_search_pages  # по умолчанию: 3
```

3 страницы × 50 = 150 резюме — на практике достаточно для 90% рекрутеров.
При необходимости можно увеличить через переменную окружения.

**Настройка:**
```env
HH_MAX_SEARCH_PAGES=3   # по умолчанию: 3
```

---

### 6. Ingestion тоже через глобальный guard (Проблемы 2 & 7 — полное покрытие)

**Файл:** `backend/app/services/ingestion_service.py` — `_fetch_resume_page()`

Фоновая индексация talent pool также проходит через `_guarded_get()`.
Если ingestion и rematch работают одновременно — оба стоят в очереди `_HH_SEM`.
